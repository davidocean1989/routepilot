## 1. 先定义输入输出

```python
optimize_route(start, waypoints, end, time_matrix, distance_matrix, objective='fastest')
```

| 输入 | 约定 |
| --- | --- |
| start | 固定起点，0-based 整数索引，拒绝 bool |
| waypoints | list / tuple，3–8 个互不重复的整数索引；输入顺序就是用户原始顺序 |
| end | 固定终点索引；None 表示在最后一个途经点结束；等于 start 表示返回起点 |
| time_matrix | N×N list / tuple 方阵，秒；第 i 行第 j 列是 i→j |
| distance_matrix | 同一地点排序的 N×N 方阵，米；与时间对应同一批路段 |
| objective | fastest 最小化总时间；shortest 最小化总距离 |

途经点不得包含起点或固定终点；除闭环最后返回起点外，每个指定地点只访问一次。不自动添加矩阵里其他地点。8 指 **8 个可排列途经点**，固定不同起终点时共有 10 个地点，矩阵为 10×10；开放路径或闭环只需 9 个地点。

矩阵必须完整，元素为有限非负 int / float，对角线已标准化为零。不要求对称或满足三角不等式。None、NaN、Infinity、负数、字符串、布尔成本、维度不符、非法索引、重复点均以 ValueError 拒绝。浮点总和溢出也拒绝。缺失/不可达边不填零、不用反向值补齐；V1 由上游补齐数据或提示无法规划。函数不能从数值识别单位或地点排序错误，上游负责核对 point_order 和单位；地图整数秒/米可避免浮点近似并列问题。

返回 JSON 可序列化 dict；Python TypedDict 定义见 [optimizer.py](../routepilot/optimizer.py)。真实固定终点 fastest 输出示例（百分比展示取两位）：

```json
{
  "objective": "fastest",
  "original": {"order": [0,1,2,3,4], "total_duration": 12138, "total_distance": 229701},
  "optimized": {"order": [0,2,1,3,4], "total_duration": 11936, "total_distance": 219006},
  "savings": {"duration": 202, "distance": 10695, "duration_percent": 1.66, "distance_percent": 4.66},
  "candidates_evaluated": 6
}
```

节省量 = 原顺序总量 − 优化顺序总量；百分比 = 节省量 / 原顺序总量 × 100。负数表示增加，不能截断成零；基线为零时百分比返回 None（JSON null），绝对节省量仍返回。优化某一目标不保证另一目标也改善。

## 2. 算法与正确性

实现位置：[routepilot/optimizer.py](../routepilot/optimizer.py)，仅依赖 Python 标准库，Python 3.10+。函数不调用网络、不修改输入、不保存全量候选，适合由后续应用层直接导入。

1. 校验输入，按用户输入顺序计算基线。
2. 用 itertools.permutations 枚举全部 k! 个途经点顺序。
3. 前置固定起点，按 end 追加固定终点或起点；开放路径不追加。
4. 按相邻有向边分别累加两份矩阵。
5. fastest 比较 `(总时间, 总距离, 索引序列)`；shortest 比较 `(总距离, 总时间, 索引序列)`，保留最小项。
6. 返回两条路线与双指标节省。

主目标相同先比较另一目标，再按索引字典序打破并列；没有把秒与米相加，输入排列变化也不改变最终并列选择（索引身份不变时）。使用浮点成本时按实际计算结果比较，不设置隐式 epsilon。

每条合法路线都与一个途经点排列一一对应。穷举覆盖全部合法路线，逐项最小化可得到当前静态矩阵、当前约束下的全局最优；有向矩阵照样成立，无需对称假设。返回起点的最后一条边包含在总成本中。

## 6. 复杂度与实际性能

令 k 为途经点数，N 为矩阵维度。时间复杂度为 **O(N² + k! × k)**（包含输入校验），算法额外空间 **O(k)**，输入矩阵占 O(N²)。流式枚举只保留当前与最佳路线，不保存 k! 条路线。固定终点和闭环有 k+1 条边，开放路径有 k 条边，候选数均为 k!。

实测环境：Python 3.11.8，macOS-15.7.9-x86_64-i386-64bit，x86_64。固定随机种子303，合成完整有向矩阵；每组预热1次、重复30次，单进程顺序执行。使用 perf_counter_ns，计时覆盖完整 optimize_route 调用，包含矩阵校验、两指标计算、并列排序及返回值构造，不含文件读取、写入、网络、解释器启动。P95取排序后的第29个样本（nearest rank）。原始30次样本、环境和代码哈希均保存在 v1-results.json。

## 7. 何时升级 OR-Tools / heuristic

V1 保持3–8途经点穷举上限。9、10、11、12途经点的候选数分别为362,880、3,628,800、39,916,800、479,001,600；这里只给组合数，未对这些规模实测，也不线性外推耗时。

以下为工程建议，尚未上线验证：

- 超过8途经点：先评估替代求解器，不直接取消当前输入上限。仍需精确解、单车静态小规模时，可评估子集动态规划（O(k²2^k)时间 / O(k2^k)空间）；测试中已用它独立核验。
- 在目标部署环境，以真实并发压测后，若8点算法P95持续超过建议预算500 ms，或CPU占用成为瓶颈，评估工作进程、缓存相同矩阵结果及替代算法。500 ms是建议预算，不是本次验收的产品承诺。
- 新增时间窗、多车、容量、取送顺序等约束时，重新建模并评估OR-Tools；此类问题属于其路由求解范围。[Google官方路由文档](https://developers.google.com/optimization/routing)
- 规模较大且接受近似解时，可评估启发式或OR-Tools局部搜索，显式设置时间限制，输出可行性与求解状态。它不保证总能返回TSP全局最优；保留本优化器作为小规模质量基准，比较最优差距与耗时。[官方TSP说明](https://developers.google.com/optimization/routing/tsp)、[搜索选项与时间限制](https://developers.google.com/optimization/routing/routing_options)

升级时仍必须保留有向边成本，不能将非对称路网当作对称问题简化。对照本轮案例、随机矩阵、失败输入及零收益行为后再替换V1引擎。

## 8. MVP 结论与下一步

**通过：V1 在固定起点、可选固定终点、3–8途经点、静态完整有向矩阵下，可以使用本优化器完成 fastest / shortest 排序与收益计算。** 代码具有独立接口与基础测试，可作为MVP路线计算模块接入。

下一步建议按顺序完成：

1. 在应用层接入地点索引映射、矩阵采集与本函数；保存矩阵版本、采样时刻、目标、原顺序和优化结果。
2. 将输入错误转成明确的产品反馈；地图层处理不完整/不可达数据，不让优化器虚构成本。
3. 在目标部署环境做真实负载压测，再确定算法延迟预算；当前没有实现服务、数据库或并发调度。
4. 使用多份真实快照核验收益稳定性，并对小幅时间收益清楚标注“预计”。

旧实验已发现：主快照最快顺序在随后两轮快照中分别比原顺序慢116秒和57秒；里程排序保持一致。详见 [snapshot-comparison.json](spike-03-evidence/snapshot-comparison.json) 与 [历史报告](spike-03-evidence/initial-report.md)。因此本次精确求解不等于稳定节省202秒，也不等于明天实际行程最优。

静态矩阵没有按每段未来出发时刻更新，不包含停车、停留时间、营业时间或其他出行限制。历史报告中的未来出发时间单段探索予以保留，但本轮未扩展该能力。shortest 只在给定矩阵每条已选路段的距离上优化访问顺序，并不重新寻找道路网络中所有路线的最短路径。
