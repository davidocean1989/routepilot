## 1. 结论与验收范围

已通过腾讯官方 MCP 实际取得五个地点的完整 5×5 驾车距离、时间矩阵。随后发现频控，尝试等待后重试仍失败；改用每批 1×4、调用结束后等待 2 秒，两轮各五次请求全部成功，取得两套完整的 20 条非对角有向边。

| --- | --- | --- |
| 多起点、多终点 | 通过 | 5×5 一次成功；2×2 一次成功；1×4 连续十次成功 |
| origins/destinations 上限 | 文档已核对，硬边界未实测确认 | 超限请求先返回频控，不能视为数量上限验证成功 |

## 3. 实际请求与完整矩阵

matrix 当前输入仅暴露必填字符串 `from`、`to`、`mode`；`origins/destinations` 是概念名称，实际参数不是这两个英文名。点内纬度在前、经度在后，多点使用英文分号。当前 schema 没有 output_schema，也没有暴露出发时间、车牌、路线策略或批次上限。

首次成功请求：2026-09-12 00:03:41.144532 +08:00，调用耗时 224 ms（不含建连，非行驶时间）。

## 4. 返回结构、单位与完整性

实际 MCP 外层为 `content` 文本数组，`structured_content=null`，需要解析其中 JSON。成功业务对象包含 `status=0`、`message`、`request_id`、`result.rows[i].elements[j]`，单元含 `distance`、`duration`。完整返回见 [matrix.json](spike-02-evidence/matrix.json) 的 events[0]。

[官方矩阵文档](https://lbs.qq.com/service/webService/webServiceGuide/route/webServiceMatrix)定义距离为米、时间为秒。矩阵的 duration **直接作为 duration_s**，不能套用 Spike 01 驾车规划乘以 60 的规则。

接入检查顺序建议：

1. 检查传输/超时异常与 MCP is_error；再解析文本 JSON。
2. 业务 status 必须为 0；MCP is_error=false 不代表业务成功。
3. rows 数量等于起点数，每行 elements 数量等于终点数，按请求顺序映射。
4. 每个正常单元的距离、时间必须是有限非负数；非对角时间缺失不能补零。
5. 检查单元 status。官方说明单元 status=4 时距离可能是直线距离且没有 duration，必须标为不可用，不能输入驾车优化器。本次未触发这种单元级返回。
6. 完整收齐所有有向边再发布一个快照；保留原始响应、请求 ID、坐标、查询时间和归一化规则。

## 5. 数量上限、频控与重复实验

### 5.1 文档上限和实测上限应分开

当前[矩阵参数文档](https://lbs.qq.com/service/webService/webServiceGuide/route/webServiceMatrix)写明：

| 请求形状 | 文档限制 |
| --- | --- |
| 一对多 | 1 个起点，最多 200 个终点 |
| 多对一 | 最多 200 个起点，1 个终点 |
| 多对多 | 每侧最多 50 个，并且 from 数 × to 数 ≤625 |

不能将其理解成 50×50 可调用；25×25 满足 625 对，50×12 也满足参数表。文档概述用 25×25 说明最大方阵；[状态码页](https://lbs.qq.com/service/webService/webServiceGuide/status)对 397 仍写多对多最多 25 个坐标，与参数表单侧 50 存在表述差异。以上按参数表记录，**当前 MCP/Key 的实际最大接受值未确认**。

本次用重复的真实坐标构造 201×1、51×2、26×25 三种超限输入，全部先返回 120。说明本次验证被频控遮挡，没有拿到预期数量错误；不能据此声称 200/50/625 已经被实测验证，也不能宣称能持续调用 25×25。没有继续申请提高配额或进行最大合法负载测试。

### 5.2 计量与账号额度

官方文档按**计算点对数**计量调用量与每秒计算量，而不是只数 MCP 请求。一份 5×5 是 25 对；跳过对角线可降到 20 对。6 个地点完整方阵为 36 对，只计算不同地点之间为 30 对。

本次未读取用户控制台，无法给出 Key 的精确 QPS、日配额或剩余额度。不能由错误反推固定额度为某个数值，也不能把首次突发成功当成持续容量。建议在控制台核对矩阵服务的计算量分配；实际扣费、失败请求是否计量也未验证。

### 5.3 实测过程与恢复结果

| 阶段 | 结果 | 证据 |
| --- | --- | --- |
| 5×5 首次请求 | 成功，25 个单元齐全 | matrix.json events[0] |
| 两次重复 5×5，调用后等 0.6 秒 | 均返回 120 | matrix.json events[1:3] |
| 2×3 | 返回 120 | matrix.json events[3] |
| 两次 1×1，互为反向 | 均成功 | matrix.json events[4:6] |
| 稍后重新连接，再测 5×5 两次、2×3 一次；调用后等 5 秒 | 仍全部返回 120 | recovery.json |
| 2×2 | 成功，四个单元齐全 | errors-limits.json events[5] |
| 1×4，每次结束后等 2 秒，共十次 | 十次全部成功，完成两轮完整非对角矩阵 | chunked.json |

拆分两轮在 00:07:01–00:07:21 发送。每轮按五个起点分别查询其余四点；每个方向均有距离和时间，没有用反向值补齐。十次延迟范围 94–437 ms，中位数 146.5 ms，仅为本次样本统计。

两轮相同方向的 20 个距离值全部一致；16 个时间值变化，最大绝对变化 131 秒。结构一致不等于数值固定，时间值应随查询时刻保存。变化与动态 ETA 语义相符，但本次不能量化路况、缓存或其他因素各自影响。每轮拆分也有数秒采样跨度，不能称为严格同一时刻快照。

## 6. 错误返回与重试建议

### 实测错误

| 输入/情况 | 业务 status | message 摘要 | MCP is_error |
| --- | ---: | --- | --- |
| 大批次及重复请求 | 120 | 此 key 每秒请求量已达到上限 | false |
| mode=invalid | 404 | 错误的请求路径 | false |
| 起点纬度 91 | 348 | 第一个点纬度范围错误 | false |
| 起点 0,0 | 348 | 坐标错误 | false |

错误外层与成功外层相同，业务错误对象没有 result。对错误响应直接索引 rows 会造成二次异常。异常 mode 在 schema 中只是 string，并没有 enum 阻止它，后续客户端应自行限制为已支持模式。

本次已实际执行等待后重试和缩小批次恢复；没有实现通用自动重试器，也没有模拟网络超时或强行耗尽日额度。

以下为 Spike 03 后续接入建议，并非已经验证的自动恢复保证：

- 120：按点对数节流，有限次数退避重试；可采用 2、4、8 秒加少量随机延迟，总尝试不超过四次。大批次持续失败时拆分，不无限重发。本次验证可用的起始设置是每批最多 4 对、调用后等待 2 秒，不能把它称为账号官方容量。
- 121（日额度耗尽）：停止，提示核对配额或等待额度恢复；不能用秒级重试解决。
- 鉴权/权限错误：停止并修正配置。参数、坐标、模式错误：修正输入，禁止原样自动重试。
- 网络故障、HTTP 429/5xx 或业务 5xx：有限次数退避，重连 MCP 后重试失败批次；此路径本次未实测。
- 单元无路、缺失时间：标记不可达/未完成，保留错误；禁止以零或直线距离悄悄替代。请求批次完成状态应独立记录，避免部分失败被误认为完整矩阵。

错误分类参考[官方状态码说明](https://lbs.qq.com/service/webService/webServiceGuide/status)；本次实际错误信息优先于预想状态码。

## 7. 对 Technical Spike 03 的输入建议

已生成 [spike-03-input.json](spike-02-evidence/spike-03-input.json)，来源为首次成功的单次 5×5 响应。它包含点顺序、POI、坐标、时间戳、请求 ID、完整 distance_m 和 duration_s、对角线处理规则以及建议的固定起终点。原始对角线仍在 matrix.json 中。

建议下次实验约定：

1. 固定起点杭州（索引 0）、终点上海（索引 4），排列南浔、乌镇、西塘三个中间点，共 3!=6 种排列。此处五个地点包含起终点，不是五个可自由排列的途经点。
2. 以总行驶秒数最少为目标，同时报告对应总里程；若要优化距离，另作独立目标，不能混合秒与米相加。
3. 基线顺序为 `[0,1,2,3,4]`。所有候选和基线使用同一份冻结矩阵，按有向边求和。不预设最优顺序，不在此 Spike 输出优化结论。
4. 这是开放路径，不加上海→杭州的回程边。只纳入行驶时间，停留、游玩、停车耗时和营业时间暂不计；以后需要时另建约束。
5. 输出最优顺序、基线/最优时间与里程、节省绝对量与比例；明确是该时刻静态 ETA 近似，不代表各路段在未来实际出发时刻的最优解。
6. 若要刷新，沿用已验证的小批次方式，完整取得 20 条有向边后生成新版本。失败时明确失败，不把新旧批次无标记地拼成一个快照。

**Go：进入 Spike 03 的离线路线优化实验。条件：保留有向性、明确单位、冻结快照、对角线归零，并遵守计算量节流。大批次持续能力和生产可用性保持未验收。**
