# RoutePilot｜一趟跑完
**副标题：一天跑 6 个地方，怎么走最顺？**

## 00｜项目立项书 v0.2

### 1. 项目背景
旅行过程中，用户经常会在一天内安排多个景点、餐厅、商圈或城市节点。

传统地图产品非常擅长解决：

> 从 A 点到 B 点怎么走。

但当用户一天需要前往 3–8 个地点时，真正的问题变成：

> 这些地点应该按什么顺序走，才能少绕路、少花时间，并顺利完成全天行程？

用户目前往往需要：
1. 自己判断各地点之间的地理关系；
2. 在地图 App 中反复查询不同路线；
3. 手动调整景点顺序；
4. 自己估算总里程和总耗时；
5. 最终再逐段导航。

如果景点分布较远，甚至涉及跨城市或跨区域，一次错误排序可能直接多出数小时路程。

RoutePilot 希望解决的不是“单段导航”，而是：

> **帮助用户规划一整天多个地点的最优访问顺序。**

### 2. 产品定位
**RoutePilot 是一个面向旅行用户的多地点智能路线规划 Agent。**

用户只需要用自然语言告诉系统：

> “我从杭州出发，今天想去南浔、乌镇、西塘，晚上到上海，怎么走最顺？”

RoutePilot 自动完成：

**地点理解 → POI/地址解析 → 路线成本计算 → 多点排序优化 → 路线报告 → 地图可视化 → 分享 → 手机导航。**

核心定位：

> **地图告诉你怎么去下一站，RoutePilot 告诉你今天应该按什么顺序去所有站。**

### 3. 核心用户
#### Primary User：一天需要前往多个地点的旅行用户
典型用户：
- 城市短途旅游用户
- 自驾旅行用户
- 跨城市一日游用户
- 周边游用户
- 需要一天安排多个景点的自由行用户

核心特点：
- 对当地地理关系不熟悉；
- 无法凭经验判断地点访问顺序；
- 不同顺序可能产生明显时间和里程差；
- 希望减少行程规划时间；
- 需要最终能直接进入地图 App 导航。

#### Future User
后续扩展：
- 销售 / 商务拜访
- 房产中介带看
- 巡店
- 日常多地点办事
- 维修人员
- 配送人员

V1 暂不针对这些场景设计复杂时间窗与业务约束。

### 4. 用户核心痛点
#### Pain 1：不知道地点应该按什么顺序去
用户知道“想去哪”，但不知道“先去哪”。

#### Pain 2：手工比较路线成本高
用户需要反复在地图 App 中切换顺序、比较距离和时间。

#### Pain 3：错误顺序可能造成明显绕路
尤其跨区域或跨城市旅行时，错误访问顺序可能多出数十公里甚至数小时。

#### Pain 4：规划与导航割裂
旅行攻略告诉用户“去哪”，地图只解决“下一站怎么走”，中间缺少“全天顺序优化”。

#### Pain 5：结果难分享
多人旅行时，规划结果往往散落在聊天记录、备忘录、地图收藏里，缺少一张统一路线。

### 5. 产品价值主张
RoutePilot 为用户提供：
- **更少绕路**：优化多个地点的访问顺序；
- **更省时间**：减少手动比路线和规划的时间；
- **结果清晰**：给出完整路线、总里程和预计时间；
- **可视化**：在地图上直接看到完整路线；
- **可分享**：生成链接，可直接通过微信传播；
- **可执行**：从路线页面直接跳转地图 App 导航。

### 6. MVP 核心 Use Case
用户输入：

> “从杭州出发，想去南浔、乌镇、西塘，最后到上海，帮我规划最顺的路线。”

系统输出：
- 推荐访问顺序；
- 总里程；
- 总预计驾驶时间；
- 每一段距离和时间；
- 相比用户原始顺序节省多少；
- 一张完整路线地图；
- 一个可分享链接；
- 每一段可直接拉起地图 App 开始导航。

### 7. V1 Scope
#### Must Have
- 自然语言输入；
- 起点；
- 3–8 个目的地；
- 可选终点；
- 地址 / POI 标准化；
- Geocoding；
- 多点距离矩阵；
- 多点时间矩阵；
- 最短时间模式；
- 最短距离模式；
- 路线排序优化；
- 总里程；
- 总驾驶时间；
- 每段路线明细；
- 地图可视化；
- 生成分享链接；
- 微信内可打开；
- 支持拉起地图 App 进行分段导航或整条路线导航（视目标地图 App 能力而定）。

#### 暂不包含
- 景点开放时间；
- 景点建议停留时长；
- 午餐安排；
- 加油 / 充电；
- 停车场推荐；
- 动态实时重新规划；
- 公交 / 高铁 / 飞机混合交通；
- 多人 / 多车协同；
- 酒店 / 门票预订。

### 8. 产品设计原则
1. **输入尽可能少**：用户只需要告诉系统“从哪里出发、想去哪里、最后去哪”。
2. **真实路线数据必须来自地图服务**：LLM 不猜路线距离与时间。
3. **LLM 理解需求，算法优化路线**：路线优化不交给 LLM 自由推理。
4. **规划和导航分开**：RoutePilot 负责全天规划；成熟地图 App 负责逐段导航。
5. **先闭环，再扩功能**：V1 先确保从输入到分享再到导航全部完成。

### 9. 初步技术框架
```text
用户自然语言输入
        ↓
RoutePilot Agent
        ↓
地点与约束解析
        ↓
腾讯位置服务 MCP
        ↓
Geocode / POI / Distance Matrix / Route
        ↓
Route Optimization Engine
        ↓
Trip Result
        ↓
Route Report Generator
        ↓
Web / H5 地图页面
        ↓
分享链接
        ↓
微信打开
        ↓
跳转地图 App 导航
```

### 10. 初步成功指标
- 地点解析成功率 ≥ 95%
- 3–8 点路线生成成功率 ≥ 95%
- RoutePilot 推荐路线相对用户原始输入顺序，在测试样本中平均节省明显时间/里程
- 从输入到结果输出 ≤ 60 秒
- 分享链接可正常在微信打开
- 路线页面可正常拉起地图导航
- 测试用户再次使用意愿 ≥ 80%

### 11. North Star Metric
**Successful Optimized Trip**

一次用户请求满足：
1. 成功识别全部地点；
2. 成功生成优化路线；
3. 用户打开结果；
4. 用户点击“开始导航”或“分享”。
